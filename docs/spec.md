> 초안. 둘이 합의 후 v1로 확정하고 포크한다. 이 문서가 계약 — 여기 없는 산출물/기능은 만들지 않고, 비교는 이 문서 기준으로만 한다.
> v0.2: 멘토 피드백(리이오·하워드, 2026-08-07) 반영 — 배포·유지보수 단계 추가, 실험 성공 기준 신설.

## 실험 목표 (멘토 피드백 반영)

AI의 도움을 받아 **앱을 끝까지 만들어서 굴리는 역량**(출시 + 운영까지)을 학습한다.

개인별 Learning Objectives는 각자 정한다 (같은 실험, 다른 배움 — 이것도 비교 포인트).

### 엘레나 (개발자, Claude) — AI의 도움을 받아 미술영감옵시디언을 만들기 위해 앱을 끝까지 만들어서 굴리는 역량에 대해서 학습하자! (검수 멘토: 리이오, 하워드)

| Learning Objective | Learning Keywords |
|---|---|
| 흐릿한 제품 아이디어를 출시 가능한 1.0 범위로 잘라내서 출시까지 | MVP, User Story Mapping |
| 디자인에서 AI를 배우기 | 사람이 만든 것처럼 만들고 싶다. |
| 사용자 행동 중 무엇을 기록할지 정해 이슈를 설계하고, 앱에 심어 데이터가 쌓이는 것을 확인할 수 있다. | Tracking Plan, Firebase Analytics, AARRR(지표 전체의 지도) |
| 출시 후 리뷰·크래시·지표를 근거로 개선 사항을 정해 업데이트를 한 차례 이상 배포할 수 있다. | ASO(앱이 검색되고 발견되게 하기), Crashlytics(어디가 부서졌는지 찾기), Phased Release(업데이트를 단계적으로 내보내기) |

멘토 피드백 메모: 리이오 "명확하댔음 굿" / 하워드 "굳이 AI로 해야 하는지" → 답: 더 잘하는 기획을 하고 싶어서 / 성공·실패 판단 기준 만들 것 (→ 위 실험 성공 기준) / 깃헙 레포로.

### 흰 (디자이너, GPT-sol) — '다양한 형태의 데이터 기록·검색·시각적 연결 방법' 학습 (검수 멘토: 리이오, 곰민)

| Learning Objective | Keywords |
|---|---|
| 미술 전공자의 아이디어 기록 과정과 불편함 | 아이디에이션 과정, 사용자 리서치, 페인포인트 |
| 아이디어의 맥락을 복원할 수 있는 정보 구조 이해 | 맥락적 메타데이터 |
| 아이디어를 분류하고 서로 연결하는 방법 | 폴더, 태그, 양방향 링크, 관계 유형 |
| 아이디어 사이의 관계를 시각적으로 표현하는 원리 이해 | 지식 그래프, 노드·엣지, 시각적 매핑 |
| AI가 기록의 맥락과 연결을 보조할 수 있는 범위 판단 | 자동 태깅, 이미지·텍스트 임베딩, 유사도 검색, 추천, Human-in-the-loop |

### 실험 성공 기준 ("성공/실패를 판단하는 기준" — 멘토 조언)

- [ ] 1.0을 실제 배포 채널에 출시했다 (스토어 심사 통과 또는 공개 배포)
- [ ] 트래킹이 동작해서 실사용 데이터가 쌓였다
- [ ] 데이터·리뷰·크래시를 근거로 한 업데이트를 1회 이상 배포했다
- [ ] 전 단계의 회고 로그가 남아 두 사람의 과정을 비교할 수 있다

넷 다 충족하면 성공. 앱의 완성도보다 **사이클을 끝까지 돈 것**이 기준이다.

## 만드는 것

미술(그림) 자료용 개인 위키 앱. 노트는 평문 `.md`, 옵시디언 볼트 호환. 플랫폼·기술 스택은 각자 자유 (여기가 비교 포인트).

## 단계별 산출물

각 단계가 끝나면 아래 산출물이 지정된 위치에 있어야 "단계 완료"다. 형식은 전부 마크다운, 상단에 날짜·버전.

### 1. 리서치 (`docs/research/`)

| 산출물 | 파일 | 완료 기준 |
|---|---|---|
| 시장조사 | `market.md` | 노트/위키 앱 시장 규모·흐름, 주요 플레이어 5개 이상 |
| 경쟁사 분석 | `competitors.md` | 옵시디언·노션 포함 3개 이상을 같은 항목(가격/핵심기능/강점/약점)으로 비교한 표 |
| 사용자 페인포인트 | `painpoints.md` | 블로그·커뮤니티 실제 발언 인용 5개 이상 + 출처 링크, 페인포인트별 분류 |

### 2. 기획 (`docs/prd/`)

| 산출물 | 파일 | 완료 기준 |
|---|---|---|
| PRD | `prd.md` | 문제 제기 → 솔루션 → 타겟 유저(1문단 페르소나) 흐름이 리서치 근거와 연결됨 |
| 기능 우선순위 | `features.md` | 기능 목록을 P0(필수)/P1(중요)/P2(나중)로 분류, P0는 5개 이하 |
| 로드맵 | `roadmap.md` | 단계별 마일스톤과 순서 (날짜보다 순서·의존관계 중심) |

### 3. 디자인 (`design/`)

| 산출물 | 파일 | 완료 기준 |
|---|---|---|
| 트렌드 리서치 | `trends.md` | 참고 사례 5개 이상 + 각각에서 가져올 것/버릴 것 한 줄씩 |
| 디자인 브리프 | `brief.md` | 디자인 원칙 3~5개, 컬러·타이포 방향, 핵심 화면 3개(노트 목록/에디터/그래프 등)의 와이어프레임 또는 스케치 |
| 에셋 정리 | `assets/` | 브리프에서 참조하는 이미지·스케치 파일, 파일명으로 구분 가능하게 |

### 4. 개발 (소스 + `docs/specs/`)

| 산출물 | 위치 | 완료 기준 |
|---|---|---|
| 동작하는 앱 | 소스 폴더 | P0 기능 전부 동작, 실행 방법이 README에 |
| 기술 스펙 | `docs/specs/architecture.md` | 스택 선택 이유, 데이터 구조(.md 저장 방식), 주요 컴포넌트 구조 |
| 기술 검토 | `docs/specs/review.md` | 알려진 한계·버그 목록 (숨기지 말 것 — 비교 데이터) |

### 5. 배포 (`docs/release/`)

| 산출물 | 파일 | 완료 기준 |
|---|---|---|
| 1.0 범위 정의 | `mvp.md` | User Story Mapping으로 자른 1.0 범위 — 뺀 기능과 뺀 이유가 명시돼 있어야 함 |
| 트래킹 플랜 | `tracking-plan.md` | AARRR 단계별로 기록할 이벤트 목록(이벤트명/트리거/속성), 앱에 심은 후 데이터 쌓이는 스크린샷 |
| 출시 기록 | `launch.md` | 배포 채널(스토어/TestFlight/웹 등), ASO 준비(이름·설명·키워드·스크린샷), 심사 통과까지의 과정 |

### 6. 유지보수 (`docs/ops/`)

| 산출물 | 파일 | 완료 기준 |
|---|---|---|
| 운영 리포트 | `metrics.md` | 출시 후 지표·리뷰·크래시(Crashlytics) 요약, 최소 1회 이상 갱신 |
| 개선 결정 | `update-1.md` | 데이터를 근거로 고른 개선 사항 → 무엇을 어떻게 바꿨는지 → 업데이트 배포 기록 (Phased Release 썼으면 그 과정도) |

### 검증 (`qa/`, 전 단계 공통)

- 개발 시작 전: P0 기능별 합격 기준을 `qa/checklist.md`에 정의 (기능당 체크 3개 이상, "동작한다" 같은 모호한 기준 금지 — 예: "노트 100개에서 검색 결과가 1초 내 표시")
- 개발 후: 체크리스트 실행 결과 기록. 최종 머지 게이트로 사용.

## 기능 목록 (P0 후보 — 기획 단계에서 각자 확정)

베이스라인 후보. 각자의 `docs/prd/features.md`에서 P0를 확정하되, **아래 ①~③은 공통 P0로 고정**한다 (이게 같아야 최종 비교·이식이 가능):

1. ① 마크다운 노트 작성/편집, 평문 `.md` 저장 (옵시디언 호환)
2. ② `[[위키링크]]` — 노트 간 연결
3. ③ 노트 목록/폴더 + 검색
4. 그래프 뷰 (위키링크 시각화)
5. 태그(#)
6. 이미지(그림 자료) 첨부·보기
7. 빠른 검색 (Cmd+K)

## 회고 로그 (전 단계 공통)

- 작업 세션마다 `docs/ai-feedback/YYYY-MM-DD-이름-주제.md` 작성 (양식: TEMPLATE.md)
- 단계 완료 시 upstream에 PR로 공유
